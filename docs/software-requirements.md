# Software Requirements

This document captures the requirements for HambotV2, derived from the implemented system, its tests, and repository conventions. It describes the software as it *should be*, so requirements stay traceable when the system changes. Sections 2.11–2.19 specify the post-1.0.0 roadmap features (see [`roadmap.md`](roadmap.md)); which of those are already implemented is tracked in the roadmap's Status section — the rest are requirements for work that is specified but not yet implemented.

## 1. Product Description

HambotV2 ("HamBot") is a Discord chat bot. It listens to messages in the guilds the bot account is a member of, recognizes messages that start with a configurable command identifier (default `!`), and executes registered commands. Command access is governed by a tiered permission system persisted in PostgreSQL and scoped per Discord guild.

## 2. Functional Requirements

### 2.1 Discord connectivity

- **FR-1**: The bot shall connect to the Discord gateway using a bot token supplied via configuration (`Secrets:BotToken`), kept outside source control (see NFR-3).
- **FR-2**: The bot shall request only the gateway intents it uses (`Guilds | GuildMessages | DirectMessages | MessageContent`), rather than `GatewayIntents.AllUnprivileged`, so Discord.Net does not warn about unused intents.
- **FR-3**: The bot shall log Discord gateway events to the host logger using a configurable log format (`BotConfiguration:LogFormat`).
- **FR-4**: The bot shall log its gateway connection state periodically (every 5 minutes) while running.
- **FR-5**: The bot shall run continuously as a background worker service until cancelled.
- **FR-6**: On host shutdown the bot shall log out and dispose the Discord client cleanly; gateway disconnects and reconnects shall be logged.

### 2.2 Command recognition

- **FR-7**: The bot shall treat any received message starting with the effective command identifier of its guild as a command invocation (per-guild override, global default `BotConfiguration:CommandIdentifier`, default `!`; see FR-26). Direct messages use the global default.
- **FR-8**: The command name shall be the first space-delimited token of the message, with the identifier stripped and the remainder lowercased before lookup.
- **FR-9**: Degenerate command invocations — identifier-only messages (e.g. a bare `!`), whitespace-only content, or empty tokens — shall be handled safely, without exceptions.
- **FR-10**: If the command name is not registered, the bot shall consult the invoking guild's custom responses (FR-54) before replying in-channel that the requested command is unavailable.
- **FR-11**: Registered commands shall be looked up by name; command names must be lowercase (enforced by unit tests).

### 2.3 Command execution & error handling

- **FR-12**: Each command shall be a class implementing `ICommand` (`Name` + `ExecuteCommand(SocketMessage, ICommandContext)`), registered at startup through the command registration chain. Commands shall also provide their help text (FR-39) as part of the implementation.
- **FR-13**: A command shall receive an execution context wrapping a database context scoped to the message being handled.
- **FR-14**: If the invoking user lacks sufficient permissions, the bot shall reply in-channel that the user is not permitted to use the command, and the command shall not execute.
- **FR-15**: A failure in a command, permission check, or database access shall produce a user-facing error message in-channel and a logged exception; it shall never stop the bot from processing subsequent messages. Exception details shall not be exposed in-channel.
- **FR-16**: Per-message resources (command handler, database context) shall always be released after handling a message, including on the failure path.

### 2.4 Permissions (per guild)

- **FR-17**: Access control shall be tier-based: a user may execute a command if and only if the user's permission tier is greater than or equal to the command's required permission tier, both evaluated within the guild the message was sent in.
- **FR-18**: Users without a database entry in the relevant guild shall default to permission tier 0.
- **FR-19**: Commands without a `CommandMetaData` database entry in the relevant guild shall default to required tier 0.
- **FR-20**: Permission tiers shall be stored per guild, per user (keyed by guild ID and Discord ID) and per command (keyed by guild ID and command name) in the PostgreSQL database.
- **FR-21**: Permission tiers shall be adjustable at runtime, without code changes or restart, via chat commands:
  - `!commandpermission <commandName> [tier]`
    - With only a command name: report that command's current tier (0 if unknown).
    - With a tier: create or update the command's tier and persist it.
  - `!userpermission <user> [tier]`
    - With only a user: report that user's current tier (0 if unknown).
    - With a tier: create or update the user's tier and persist it.
- **FR-22**: The `!userpermission` command shall accept a Discord mention (`<@id>` / `<@!id>`) as well as a raw numeric Discord ID as the user argument.
- **FR-23**: The permission-management commands themselves are subject to the same permission checks as any other command (their own tiers can be raised via `!commandpermission`).
- **FR-24**: The bot shall support membership in multiple guilds simultaneously, with all persisted state (user tiers, command metadata, settings) scoped per guild. A user's tier or a command's required tier in one guild shall have no effect in any other guild.
- **FR-25**: Commands received outside a guild (direct messages) shall run in a defined **DM scope**: the invoking user holds owner tier (the configured bot owner tier 4), commands require their built-in default permission tiers, and no per-guild state shall be read or written — permissions cannot be adjusted from direct messages. Commands that manage per-server state (`!userpermission`, `!commandpermission`, `!settings`, `!agenttier`) shall decline in direct messages with a clear in-channel message.
- **FR-26**: Bot configuration options (e.g. the command identifier) shall be configurable per guild, with the global `appsettings.json` values acting as defaults for guilds without explicit settings.
- **FR-33**: Named tier levels shall be defined for the permission scale (e.g. 0 = everyone, 1 = moderator, 2 = admin, 3 = owner) and documented, so commands and users can be assigned roles by name rather than by arbitrary numbers.
- **FR-34**: Each guild shall have a bootstrap administrator: the guild owner shall automatically hold the highest guild-level tier (owner) in that guild, without any prior database setup, so administration is possible from the first message. (The globally highest tier, bot owner, is defined by FR-41; there is no separate configured-admin id — the bot owner supersedes it.)
- **FR-35**: The permission-management commands (`!commandpermission`, `!userpermission`) shall have a built-in default required tier of admin (see FR-33), overriding the general default of FR-19 for these commands, so unprivileged users cannot self-promote on a fresh guild.
- **FR-36 (escalation guard)**: A user may only assign permission tiers strictly lower than their own tier. A user shall not be able to modify their own tier or the tier of a user whose tier is equal to or higher than their own.
- **FR-37**: Assigned tiers shall be validated: integers within the defined tier scale (non-negative, not exceeding the highest defined tier). Invalid input shall produce an in-channel error message.
- **FR-38**: A `!help` command shall list the commands available to the invoking user (i.e. commands whose required tier in the current guild is at most the user's tier), so users and staff can discover what they can run. The list is paginated at 10 commands per page, with a character-budget guard so no page exceeds Discord's message-length limit.
- **FR-39**: Each registered command shall expose help text: a short description and a usage/argument summary, supplied with the command implementation (see FR-12) so it stays in sync with the code.
- **FR-40**: Invoking `!help <commandName>` shall display the detailed help text (description, usage, required permission tier) for that command. Detailed help shall only be shown for commands the invoking user can run; requesting help for an unavailable or unknown command shall produce an in-channel message saying so, without revealing whether the command exists at a higher tier.
- **FR-41 (bot owner)**: A bot owner Discord ID shall be configurable via settings (`Permissions:BotOwnerDiscordId`; `BOT_OWNER_DISCORD_ID` in the container `.env` file). The bot owner shall automatically hold the highest permission tier of all (bot owner, above the guild-level tiers of FR-33) in every guild, and shall be the designated authority for features that apply across guilds (global settings and defaults). The bot owner tier shall be configuration-only and can never be assigned through the permission-management commands.

### 2.5 Persistence & startup

- **FR-27**: User permission data shall be persisted across restarts in PostgreSQL via EF Core (`User` entity keyed by guild ID and `DiscordId`).
- **FR-28**: Command permission metadata shall be persisted across restarts in PostgreSQL via EF Core (`CommandMetaData` entity keyed by guild ID and `CommandName`).
- **FR-29**: The database connection string shall be supplied via configuration (`ConnectionStrings:DefaultConnection`), kept outside source control.
- **FR-30**: The bot shall apply EF Core database migrations automatically on startup.
- **FR-31**: If the database is unreachable at startup, the bot shall fail fast with a clear error message and a non-zero exit code, instead of starting in a degraded state.
- **FR-32**: Missing or invalid required configuration keys (`Secrets:BotToken`, `ConnectionStrings:DefaultConnection`, `BotConfiguration:BotName`, `BotConfiguration:LogFormat`, `BotConfiguration:CommandIdentifier`) shall be detected at startup, before any connection attempt, and reported with an explicit error naming the offending key.

### 2.6 Quotes (per guild)

- **FR-42**: The bot shall store quotes scoped per guild: a `Quote` entity shall be persisted via EF Core in PostgreSQL (covered by the automatic startup migrations, FR-30), recording the quote text, the Discord ID of the user who added it, and the timestamp of the adding message. A quote created in one guild shall never be visible, searchable, or removable in any other guild (per-guild scoping, FR-24).
- **FR-43**: Each quote shall carry a per-guild number that acts as a simple sequential index, **0-based like the old bot's index-based quote list (the first quote is number 0)**: every new quote is assigned one greater than the guild's current maximum number, so the number increases by one with each quote added. Removing a quote shall never change the numbers of the remaining quotes.
- **FR-44**: `!quote` with no arguments shall reply in-channel with a random quote from the invoking guild, prefixed with its number. If the invoking guild has no quotes, the bot shall reply with a friendly "no quotes yet" message instead of an error.
- **FR-45**: `!quote <number>` shall reply in-channel with that exact quote, prefixed with its number. An unknown number shall produce an in-channel error message, never an exception or an empty reply. An argument that does not parse as a number (including numeric-looking values outside the representable range) shall be treated as quote text to add (see FR-47).
- **FR-46**: `!searchquotes <text...>` shall reply in-channel with the invoking guild's quotes whose text contains the search string, matched case-insensitively, each result prefixed with its number, capped at 10 results. If no quotes match, the bot shall reply with a "no matching quotes" message. Empty search text shall be rejected with an in-channel error.
- **FR-47**: `!quote <text...>` — any argument that is not a number — shall add the text as a new quote in the invoking guild (quoting is a single, immediate action) and reply with the assigned number. Quote text shall be capped at 2000 characters (Discord's message limit); longer text shall be rejected with an in-channel error. When a quote reply — a maximal quote plus its number prefix, or a search result list of up to 10 quotes (FR-44–FR-46) — would exceed Discord's message limit, the reply shall be trimmed to fit with a trailing ellipsis; the stored text shall never be modified.
- **FR-48**: `!removequote <number>` shall remove that quote from the invoking guild and confirm in-channel; an unknown number shall produce an in-channel error. `!removequote` shall have a built-in default required tier of moderator (FR-33), overriding the general default of FR-19; `quote` (both fetching and adding) and `searchquotes` shall default to tier 0 (everyone).
- **FR-49**: Quote commands shall be subject to the standard command pipeline behavior: runtime permission adjustment via `!commandpermission` (FR-21), per-tier cooldown throttling (NFR-12), typed argument parsing through the shared mechanism (NFR-13), help text (FR-39, FR-40), and lowercase names (C-4).
- **FR-50**: Quote commands manage per-guild state and shall therefore decline in direct messages with the established "only available in servers" message (consistent with FR-25).

### 2.7 Custom command responses (per guild)

- **FR-51**: The bot shall support user-defined text responses scoped per guild: a `CustomResponse` entity shall be persisted via EF Core in PostgreSQL (covered by the automatic startup migrations, FR-30), recording the response name, its content, the Discord ID of the user who last modified it, and created/updated timestamps. A response defined in one guild shall have no effect in any other guild (per-guild scoping, FR-24).
- **FR-52**: Response names shall be a single lowercase token of 1–32 characters, consisting only of lowercase letters, digits, hyphens, and underscores. Invalid names shall be rejected with an in-channel error.
- **FR-53**: A response shall not take the name of a registered built-in command: creation shall reject such names with an in-channel error. Built-in commands shall always win dispatch — a custom response can never shadow a built-in, including built-ins added later.
- **FR-54**: When a command token matches no built-in command, the bot shall look up the invoking guild's custom responses before replying "unavailable"; a match shall reply in-channel with the stored content.
- **FR-55**: Custom response invocations shall go through the same checks as built-in commands: the per-(guild, user, command) cooldown throttle keyed on the response name (NFR-12), and a permission check defaulting to tier 0 whose required tier shall be adjustable at runtime via `!commandpermission` (FR-21), stored as regular `CommandMetaData` (FR-19, FR-28).
- **FR-56**: `!addresponse <name> <content...>` shall create the response, or — if the name already exists in the guild — update its content and modification fields; the reply shall distinguish "created" from "updated". Empty content shall be rejected with an in-channel error; content shall be capped at 1000 characters. The command shall have a built-in default required tier of moderator (FR-33), overriding the general default of FR-19.
- **FR-57**: `!removeresponse <name>` shall delete that response from the guild and confirm in-channel; an unknown name shall produce an in-channel error. The command shall have a built-in default required tier of moderator (FR-33), overriding the general default of FR-19.
- **FR-58**: `!listresponses` shall list the invoking guild's response names alphabetically; a guild with no responses shall get a message saying so. The command shall default to tier 0 (everyone).
- **FR-59**: Custom responses shall not apply in direct messages (they are guild state): in DMs an unknown token shall keep the normal "unavailable" reply. The response-management commands (`!addresponse`, `!removeresponse`, `!listresponses`) manage per-guild state and shall decline in direct messages with the established "only available in servers" message (consistent with FR-25).
- **FR-60**: A custom response shall consist of text content only. File or image attachments on the `!addresponse` invocation shall be neither stored nor replayed — such invocations shall be rejected with an in-channel error — and a dispatched response shall never include an uploaded file. Links in the content (e.g. `!addresponse <name> <image link>`, the expected most common use case) are ordinary text: they are stored verbatim and sent as a plain text reply, with any link preview or embed rendered by Discord client-side. The bot shall upload no files itself.

### 2.8 Reminders (user-scoped)

- **FR-61**: The bot shall support timed reminders scoped per user: a `Reminder` entity shall be persisted via EF Core in PostgreSQL (covered by the automatic startup migrations, FR-30), recording the reminder message, the due time in UTC, the owner's Discord ID, and the guild ID of creation (null when created in a direct message). Reminders are personal (user-scoped, not guild-scoped) and work from both guild channels and direct messages.
- **FR-62**: `!remindme <duration> <message...>` shall parse the duration from leading number+unit tokens: units `s`, `m`, `h`, `d`, `w` with long forms (`seconds` … `weeks`) accepted, compact (`10d 5h`) and spaced (`10 d 5 h`) forms both valid, and multiple tokens summed (e.g. `!remindme 1d 12h water the plants`). The message shall be the remainder of the invocation, non-empty and capped at 500 characters.
- **FR-63**: The total duration shall be positive — there shall be no minimum or maximum bound: durations of years are accepted. Anything unparsable or non-positive shall produce an in-channel error with a usage hint, and nothing shall be stored.
- **FR-64**: On success the reminder shall be persisted (FR-61) and the bot shall confirm in-channel, echoing the message and the due time.
- **FR-65**: A hosted background service shall deliver each due reminder as a direct message to the owner containing the reminder message, second-accurate: it shall schedule its next wake-up at the earliest pending due time instead of polling on a fixed coarse interval, re-scheduling when a newly created (or cancelled) reminder becomes the earliest, with a bounded fallback poll (every 10 seconds) to cover clock drift and missed wake-ups. Delivered reminders shall be removed from the pending set. Delivery shall never block or crash the service.
- **FR-66**: Reminders shall survive restarts: the pending set is persisted, and a reminder that became due while the bot was down shall be delivered once the service starts.
- **FR-67**: A delivery failure (e.g. closed DMs) shall be retried a bounded number of times and then marked failed and logged; it shall never block other reminders and never produce a user-facing crash.
- **FR-68**: `!reminders` shall list the invoking user's pending reminders (number, due time, message), soonest first, capped at 10 entries.
- **FR-69**: `!cancelreminder <number>` shall cancel one of the invoking user's own pending reminders (numbers from `!reminders`) and confirm; users shall never be able to see or cancel another user's reminders. Unknown or foreign numbers shall produce an in-channel error.
- **FR-70**: A per-user cap of 10 pending reminders shall be enforced; exceeding it shall produce an in-channel error instead of storing the reminder.
- **FR-71**: The reminder commands (`!remindme`, `!reminders`, `!cancelreminder`) shall default to tier 0 (everyone) and be subject to the standard command pipeline behavior: per-tier cooldown throttling (NFR-12) and help text (FR-39, FR-40). Because reminders are user-scoped, not guild-scoped, all three shall remain fully usable in direct messages (DM scope, FR-25).

### 2.9 Quote import (legacy migration)

- **FR-72**: The bot owner shall be able to import the old bot's quotes into a guild: `!importquotes`, run in the target guild with the old bot's `quoteSettings.json` attached as a file to the invocation message. The command shall download the attachment from its Discord CDN URL and parse the legacy format — a JSON object with a `quotes` array whose entries carry a `quote` text and an optional `date` timestamp.
- **FR-73**: Imported quotes shall be appended to the invoking guild in file order, continuing the per-guild sequential numbering (FR-43). Each imported quote shall record the Discord ID of the importing user as `AddedByDiscordId` and shall take its `CreatedAt` from the legacy entry's `date` when present, falling back to the import message's timestamp otherwise.
- **FR-74**: The import shall be all-or-nothing: an unreadable or malformed attachment, a file containing no quotes, or any entry whose text is empty or longer than 2000 characters (FR-47) shall produce an in-channel error naming the problem, and nothing shall be stored. The file itself has no size or quote-count limit.
- **FR-75**: `!importquotes` shall have a built-in default required tier of **bot owner (tier 4)** — a tier reachable only through configuration (FR-37), so only the configured bot owner can ever run it. It is subject to the standard command pipeline behavior (FR-49) and, because it writes guild state, declines in direct messages (FR-50).

### 2.10 Version reporting

- **FR-76 (build version)**: Every build of the bot shall embed a version string derived from source control: the semver of the most recent `v`-prefixed git tag reachable from the built commit, plus the built commit's abbreviated (7-character) hash, formatted as semver build metadata (e.g. tag `v1.2.3` at commit `1639324…` → `1.2.3+1639324`). The version shall be embedded into the binary at build time in every deployment mode (source run, plain Docker, Compose) so a running bot always reports the exact code it was built from. Builds whose commit has no reachable tag shall report the fallback semver `0.0.0` plus the commit hash; builds without git metadata shall report `0.0.0+unknown`. A running bot shall never report a version that misidentifies its code as a released one.
- **FR-77 (`!version`)**: A `!version` command shall reply in-channel with the bot's current version string — the embedded build version (FR-76). It shall have a built-in default required tier of 0 (everyone), shall work in direct messages (it reads no guild state, FR-25), and shall provide help text like every command (FR-39, FR-40).

### 2.11 Discord presence & profile identity

- **FR-78**: The bot shall maintain a Discord presence — an activity (type `playing`, `watching`, `listening`, or `competing`) with a status text — applied through a single presence service used by every source of presence changes (startup configuration, the `!presence` command FR-79, the LLM presence job FR-93, the MCP `set_presence` tool FR-88). An optional configuration section (`BotConfiguration:Presence:Type`, `BotConfiguration:Presence:Text`) shall set the initial presence once the gateway is ready; when absent the bot shall set no activity. The text shall be capped at 128 characters and the type limited to the four supported values; invalid configured values shall be reported at startup as a named-key configuration error and fail fast. Streaming activities are out of scope (see §6).
- **FR-79**: A `!presence` command shall manage the presence at runtime: with no arguments it shall report the current activity type and text (or that none is set); `!presence <type> <text...>` shall validate type and text (in-channel errors otherwise, with the same limits as FR-78) and apply the new presence immediately; `!presence clear` shall remove the activity. Its built-in default required tier shall be bot owner (FR-41) — the presence is a global, cross-guild bot identity — and it shall work in direct messages (it touches no guild state, FR-25). Runtime presence changes shall not persist across restarts: the startup configuration reapplies.
- **FR-80**: Concurrent presence updates shall be serialized so that exactly one applies at a time, with the last request winning. A failure to apply (e.g. a Discord error during a reconnect) shall be logged, surfaced as an in-channel error when it originates from a command, and shall never crash the bot.
- **FR-113**: The bot shall maintain its profile "About Me" (bio) alongside its presence, through the same service (same serialization, last-write-wins, and failure semantics as FR-80). An optional configuration value (`BotConfiguration:Bio`, at most 190 characters, line breaks allowed) shall set the bio once the gateway is ready; when absent, the bio shall be left untouched at startup. Because bots set their bio through Discord's per-guild member route, the bot shall apply its bio in every guild it is a member of. A `!bio` command shall manage the bio at runtime: with no arguments it reports the current bio (or that none is set); `!bio <text...>` validates (in-channel errors otherwise, same limits) and applies immediately; `!bio clear` removes it. It shall have a built-in default required tier of bot owner (FR-41), work in direct messages (no guild state is touched, FR-25), and provide help text (FR-39). Runtime bio changes shall not persist across restarts; a restart reapplies the configured bio when one is set.
- **FR-115**: A `!avatar` command shall manage the bot's profile picture at runtime, with a built-in default required tier of bot owner (FR-41), working in direct messages, and providing help text (FR-39): with no arguments it replies with the current profile picture's CDN URL; an invocation carrying exactly one image attachment, or a single image URL as its argument, shall download the image, validate it (image content, within Discord's documented image limits — in-channel errors otherwise, nothing changed), and apply it — per guild through the member route like the bio (FR-113), plus the bot's global avatar where Discord supports it. `!avatar reset` shall remove the custom images, falling back to the application default. There is no startup configuration for images; runtime changes are not persisted, and a restart leaves the Discord-side state untouched.
- **FR-116**: A `!banner` command shall manage the bot's profile banner with the same shape and semantics as `!avatar` (FR-115): with no arguments it replies with the current banner's CDN URL or that no banner is set; an image attachment or image URL sets the banner per guild through the member route; `!banner clear` removes it. The same tier, DM availability, help text, validation, and failure handling apply.

### 2.12 Database backups

- **FR-81**: The PostgreSQL database shall be backed up automatically on a configurable schedule (default once per day) by a dedicated backup service in the deployment (a docker-compose `backup` service), producing timestamped, compressed custom-format `pg_dump` files in a configurable persistent local backup directory. The interval and the local retention count (default 7 most recent dumps) shall be configurable via environment; older local dumps shall be pruned only after a new dump has been written successfully, so a failed dump never deletes good backups.
- **FR-82**: After each successful local dump, the backup service shall push the dump file to configurable S3-compatible offsite storage (endpoint, bucket, and credentials via environment only). Offsite storage shall be optional: with no remote configured, the push step is skipped. A failed push shall be logged and shall affect neither the local dump, its retention, nor the bot.
- **FR-83**: A scripted restore procedure (`scripts/restore-backup.sh <dump-file>`) shall restore a dump into the deployment's database: stop the bot, restore into a recreated database, restart the stack, and verify the known startup lines (the same verification as the deploy pipeline). The procedure shall be documented and proven once in a restore drill against a scratch database (NFR-19).
- **FR-84**: Backups shall run independently of the bot process: the database is backed up on schedule even while the bot container is stopped, restarting, or failing.
- **FR-85**: Backup credentials (database password, offsite storage credentials) shall be supplied exclusively via environment/secrets (the gitignored `.env` file), never committed; backup dumps contain database content only.
- **FR-96**: A `!backup` command shall trigger an on-demand backup immediately — the same dump format and the same shared backup directory as the scheduled backups (FR-81) — and reply in-channel with the dump's file name and size. It shall have a built-in default required tier of bot owner (FR-41), work in direct messages (a global operation touching no guild state, FR-25), and provide help text (FR-39). A failure shall produce an in-channel error and leave the scheduled backup cycle unaffected.
- **FR-97**: A `!backups` command shall list the available backups (the dump files in the shared backup directory) newest first — name, timestamp, and size — capped at 10 entries; an empty directory shall produce a friendly message instead of an error. It shall default to bot owner tier (FR-41), work in direct messages, and provide help text (FR-39).
- **FR-98**: A `!restorebackup <name>` command shall restore a listed backup into the live database as a two-step, explicitly confirmed operation: a first invocation shall reply with a warning that all current data will be replaced and instruct the operator to repeat the invocation with `confirm` appended; only `!restorebackup <name> confirm` shall execute the restore (dropping and recreating existing database objects from the dump). While a restore runs the bot shall be in **maintenance mode**: other commands reply with a maintenance notice, the MCP `run_command` tool (FR-90) is declined with the same captured notice (its invocations run through the same pipeline), and the scheduled reminder delivery engine defers its deliveries — no reminder may be marked failed due to a running restore. After a successful restore, caches derived from the database (guild settings) shall be invalidated. The command shall default to bot owner tier (FR-41), work in direct messages, and provide help text (FR-39). The scripted procedure (FR-83) remains the authoritative recovery path when the bot itself is unavailable; the command is the convenient path for reverting a healthy bot to a known-good backup.

- **FR-100**: Every backup shall be validated before it counts: immediately after writing, the dump is verified by a restore-catalog listing of the file plus a minimum size floor. A dump that fails validation is logged as a failed backup, does not count toward retention, is not pushed offsite, and raises a watchdog alert (FR-106). Retention (FR-81) always keeps the most recent *valid* dumps.
- **FR-101**: The backup service shall periodically prove restorability with an automated restore test on a configurable schedule (default monthly): restore the newest valid dump into a scratch database created for the test, verify the expected tables exist, drop the scratch database, and record the outcome — consumable by `!health` (FR-105) and the watchdog (FR-106); a failed test is logged and alerts. The operator restore drill (FR-83/NFR-19) remains the authoritative proof of the full deployment path.

### 2.13 MCP server (Odysseus integration)

- **FR-86**: The bot shall host an MCP (Model Context Protocol) server over streamable HTTP at a configurable listen address, as an opt-in feature: active only when `Mcp:Enabled` is true and `Mcp:ApiKey` is set, disabled by default. The startup log shall state whether the MCP endpoint is running and where it listens. The endpoint shall not be reachable from outside the deployment host (loopback-only publish in compose).
- **FR-87**: Every MCP request shall be authenticated with the configured API key (bearer); requests without a valid key shall be rejected before any tool logic runs. The key is secret-handled like the other credentials (NFR-3, NFR-4).
- **FR-88**: The MCP server shall expose status & identity tools: `bot_status` (build version FR-76, uptime, connected guild count, current presence and bio), `list_guilds` (guild ids and names), and `list_commands` (every registered command's name, default permission tier, description, and usage — the discoverable surface for `run_command`, FR-90), plus `set_presence` and `set_bio` (same validation, limits, and services as FR-78/FR-79/FR-113).
- **FR-89**: The MCP server shall expose messaging tools: `get_recent_messages(channelId, limit)` — recent channel messages fetched through Discord's REST API within the bot's existing channel access, capped at 50 — and `send_message(channelId, text)` — a plain-text message capped at 2000 characters; no files or embeds (consistent with the text-only stance of FR-60).
- **FR-90**: The MCP server shall expose `run_command(guildId, commandLine)`, which executes through the existing command pipeline (FR-7–FR-16) as the bot owner (tier 4, FR-41): the same permission, cooldown, custom-response-dispatch, and error semantics apply, and the standard command audit event (NFR-11) fires. The invocation is virtual — the command's in-channel reply is captured and returned as the tool result and is never posted to a real channel; posting to channels is `send_message`'s job (FR-89).
- **FR-91**: MCP tool invocations shall be traceable from logs (one structured event per call: tool name and outcome) without message content in routine events (NFR-11 spirit). A failing tool call shall be logged and returned as an error result, and shall never crash the endpoint or the bot.
- **FR-120**: The bot shall support a per-guild operator-agent tier, setting the effective tier of the `run_command` virtual user (FR-90) in that guild: commands whose required tier exceeds it are denied exactly like any other invocation (cooldowns, audit, and the denial reply unchanged). The default is the lowest tier (0) — the agent can run only what everyone can until a guild raises it. The tier is stored per guild (`GuildSetting.OperatorAgentTier`, null = default) and adjusted at runtime via the `!agenttier` command — no arguments report the current tier, `<tier 0-4>` sets it, `clear` resets it to the default. The command is guild-scoped (it declines in direct messages like the other per-server management commands, FR-25), defaults to owner tier (3) so the guild owner or the bot owner may change it (FR-41), and provides help text (FR-39). An operator-agent invocation of the command itself shall be declined, so the agent can never change the ceiling that governs it. The resolved tiers are cached per guild and invalidated together with the other guild settings after a backup restore (FR-98).

### 2.14 LLM integration (phase 1: presence updates)

- **FR-92**: The bot shall integrate the Mistral API through a dedicated LLM client, configured via `Llm:ApiKey` (secret, NFR-3) and `Llm:Model` (default `mistral-small-latest`). All LLM features shall be inactive when no key is configured — the bot runs fully without any LLM functionality.
- **FR-93**: The bot shall support automatic LLM-generated presence updates: an opt-in background job (`Llm:PresenceUpdates:Enabled`, default false) that on a configurable interval (default 60 minutes) asks the LLM for a new activity text — the prompt carrying a configurable persona seed (`Llm:Persona`), the bot's name and version, the current date/time, and the current presence — validates the result (non-empty, single line, at most 128 characters after trimming), and applies it through the presence service (FR-78/FR-80).
- **FR-94**: LLM or API failures — request errors, empty, multi-line, or over-limit output — shall leave the current presence unchanged, be logged, and be retried on the next interval; they shall never crash the bot or the job.
- **FR-95**: The LLM client shall be abstracted behind an interface with a Mistral HTTP implementation, so all prompt-construction, output-validation, and scheduling logic is unit-testable without network access.
- **FR-99**: The bot shall ship with a documented default persona seed (its voice and character) used when `Llm:Persona` is unset (FR-93); authoring and tuning this persona is part of the LLM feature work (see [`roadmap.md`](roadmap.md)). Overriding it via configuration changes nothing else.
- **FR-102**: The LLM client shall account usage per feature (e.g. presence updates) and per UTC calendar day — requests and tokens in and out — and expose the current day's usage to `!llm status` (FR-104) and `!health` (FR-105). Accounting is in-memory (it resets on restart); restarts are operator actions that the watchdog observes, which bounds the reset exposure.
- **FR-103**: A configurable daily request budget (`Llm:DailyRequestBudget`, default 500) shall hard-stop all LLM API calls for the rest of the UTC day once exhausted: features skip their work — the presence job skips its tick without changing the presence, like any other failure (FR-94) — the stop is logged, and the watchdog alerts (FR-106). Usage resumes at the next UTC day rollover. A budget of `0` disables the LLM feature set like an absent key (FR-92).
- **FR-104**: A `!llm` command shall manage the LLM features at runtime, with a built-in default required tier of bot owner (FR-41), working in direct messages, with help text (FR-39): `!llm status` reports each feature's enabled state, the kill switch, and today's usage against the budget (FR-102/FR-103); `!llm off` suspends all LLM API calls at runtime until `!llm on` or a restart (a restart restores the configured state); `!llm on` re-enables. The kill switch is in-memory and logged; it never disables the accounting.
- **FR-114**: When `Llm:BioUpdates:Enabled` (default false) is set, the LLM job shall also refresh the bio (FR-113): on its interval it generates a new bio text (non-empty, at most 190 characters, line breaks allowed) from the same persona seed and prompt material (FR-93), validates it, and applies it through the shared service. The failure handling of FR-94 applies unchanged (keep the current bio, log, retry next tick), and bio generation counts against the daily budget like any other LLM call (FR-102/FR-103).

### 2.15 Watchdog, health reporting & operator notifications

- **FR-105**: A `!health` command shall report the bot's current operational state in-channel: build version (FR-76), uptime, gateway connection state, database reachability, the last successful backup and last restore-test outcome (FR-100/FR-101, read from the shared backup status), the LLM state (configured, feature states, kill switch, today's usage against the daily budget, FR-102–FR-104), the MCP endpoint state (FR-86), the pending reminder count, and the configured notification channel (FR-117). It shall have a built-in default required tier of bot owner (FR-41), work in direct messages (it reads no guild state, FR-25), and provide help text (FR-39).
- **FR-106**: A watchdog background service shall periodically (configurable, default every 5 minutes) detect operator-relevant degradation and alert the bot owner (FR-41) by direct message: gateway disconnected longer than a configurable threshold (default 10 minutes); backups failing validation, overdue (no successful backup within the scheduled interval plus a grace margin), or a failed/overdue restore test (FR-100/FR-101); the LLM daily budget exhausted (FR-103) or repeated LLM failures (three consecutive, FR-94); and maintenance mode active (FR-98). Each condition shall alert once when first detected and re-alert at most once per hour while it persists; recovery shall be logged and announced once. Alerts shall additionally be posted to the configured notification channel when one is set (FR-117/FR-118). Without a configured bot owner, the watchdog shall log alerts only. A failing watchdog check shall never crash the bot.
- **FR-117**: The bot shall support an operator notification channel: a channel where errors, failures, and critical conditions are posted. The channel shall be configurable via an optional configuration key (`Notifications:ChannelId`) and adjustable at runtime by the bot owner via a `!notifychannel` command — no arguments report the current channel (or that none is set); `!notifychannel <channel>` (a channel mention or raw channel id) sets it and persists the setting across restarts in global key-value storage (the first key of a `BotSetting` entity, configuration only being the fallback default); `!notifychannel clear` unsets it. The setting is global (bot-owner scope, FR-41); the command shall default to bot owner tier, work in direct messages, and provide help text (FR-39).
- **FR-118**: When a notification channel is configured (FR-117), the bot shall post operator notifications there: watchdog condition alerts and recoveries (FR-106), command execution failures (the FR-15 error path), scheduled reminder deliveries that exhausted their retries (FR-67), maintenance-mode entry/exit and restore outcomes (FR-98), and notification delivery failures themselves (which additionally reach the bot owner by direct message and the logs). Notifications shall be rate-limited (a configurable post cap per minute, default 5) with identical consecutive messages collapsed, so an error storm (e.g. a database outage failing every command) cannot flood the channel. A failure to post a notification shall be logged and shall never affect the originating feature. Startup criticals cannot be notified in-channel (the gateway is not connected yet) and remain log-only. With no channel configured, notifications degrade to logs and the bot owner's direct messages.

### 2.16 Recurring reminders

- **FR-107**: `!remindme every <duration> <message...>` shall create a recurring reminder: first due after the duration, and — unlike a one-shot reminder (FR-62) — re-scheduled for the next interval each time it is delivered, from the actual delivery time, so downtime shifts the schedule instead of piling up a burst of catch-up deliveries. Duration parsing, units, and message validation reuse the one-shot rules (FR-62/FR-63); the recurrence interval shall have a configurable minimum (default 10 minutes), enforced with an in-channel error.
- **FR-108**: Recurring reminders keep their number across deliveries and are managed by the existing commands: `!reminders` lists them (marked as recurring, with their interval, FR-68), and `!cancelreminder <number>` permanently cancels one (FR-69). A recurring reminder that exhausts its delivery retries (FR-67) stops repeating and is marked failed like a one-shot.
- **FR-109**: Recurring reminders shall be subject to a per-user cap separate from the one-shot cap (FR-70) — configurable, default 5 — with an in-channel error at the cap; they shall never consume one-shot cap slots.

### 2.17 Discord application commands (slash commands)

- **FR-110**: The bot shall expose a subset of its registered commands as Discord application commands (slash commands), opt-in via configuration (`SlashCommands:Enabled`, default false). Three families are eligible: administrative/configuration commands (permissions, guild settings, bot profile and identity, backups and restore, health, notification channel, LLM toggles — i.e. `!commandpermission`, `!userpermission`, `!settings`, `!agenttier`, `!presence`, `!bio`, `!avatar`, `!banner`, `!backup`, `!backups`, `!restorebackup`, `!health`, `!notifychannel`, `!llm`, and — when that feature lands — `!quoteoftheday` *(planned, FR-128)*), commands that act solely on the invoking user's own state (the reminder commands `!remindme`, `!reminders`, `!cancelreminder`), and `!help` (exposed as `/help`, FR-119 — the discovery command for both surfaces). The remaining community-facing chat commands — the quote and custom-response commands and `!version` — remain text-only. Eligibility is declared explicitly per command implementation; the registration pass builds one slash definition per eligible command from the same command registry as the text surface — name and description derived from the command's `Description` (FR-39), typed options derived from per-command application-command metadata, and a single free-form `arguments` string option for commands without such metadata. Definitions shall be synchronized with Discord on startup (bulk overwrite, idempotent). Custom responses are not registered as application commands (see §6).
- **FR-111**: A slash invocation shall execute through the same command pipeline as a text invocation: the interaction is converted to its equivalent command line and handled by the real command handler — identical permission tiers for the invoking user and guild (FR-17–FR-25), identical cooldown keys (a user's slash and text invocations of the same command share the throttle, NFR-12), the same audit event (NFR-11), and the same error semantics (FR-15, no exception details). Slash invocations in direct messages run in the DM scope (FR-25).
- **FR-112**: Replies to slash invocations shall be visible only to the invoker: the interaction is acknowledged immediately (deferred, ephemeral), and every reply — the command's normal output and the pipeline's denials (permission, cooldown, maintenance, the generic error) alike — is posted as an ephemeral response visible only to the invoker, so a slash invocation stays a private conversation with the bot (Discord's own "used /command" usage line is outside the bot's control). Reply text is identical to the text surface, so command behavior never differs between surfaces — only its visibility does. The text surface remains unchanged and public (coexistence): every command stays invokable as text, and `!help`/`/help` (FR-38, FR-40, FR-119) documents the full command set regardless of surface.

- **FR-119**: A multi-page help list (FR-38) shall carry interactive pagination: a previous/next button pair attached to the list message on both surfaces — the text-surface message and the interaction reply — with each button's custom id encoding the invoker it belongs to and the page it requests, and the buttons at the list's bounds disabled. Paging is invoker-owned: a click by anyone but the user the list was rendered for shall produce an ephemeral denial visible only to the clicker, without executing any command, leaving the paginated message unchanged. The invoker's own click shall execute as a `help <page>` invocation of the invoker through the same command pipeline as a slash invocation (FR-111 semantics: the invoker's permission tiers, cooldown, audit event, and error semantics, including the DM scope), and the paginated message shall then be updated in place with the new page's text and rebuilt buttons; a declined click (permission, cooldown, maintenance) shall produce an ephemeral denial visible only to the clicker, leaving the paginated message unchanged. An out-of-range click (only possible if a list shrank between renders) shall produce the same friendly out-of-range reply the text surface gives, ephemerally and without modifying the paginated message. Button handling shall be active regardless of `SlashCommands:Enabled`, because the buttons ride on text-surface messages too; a single-page list carries no buttons.

### 2.18 Dependency security scan (weekly Jenkins job)

- **FR-121**: A scheduled Jenkins build shall run the dependency security scan weekly (cron trigger, default Sundays 04:00 UTC, configurable in the Jenkins job) without operator action: it checks out `master`, restores, and builds the solution with the same command and warning policy as the normal Build stage (NFR-6). The scan job shall never deploy: it shares no path with the Deploy stage and holds no deploy credentials, so no scan run — successful, failed, or compromised — can reach the production stack.
- **FR-122**: The scan job shall generate a CycloneDX SBOM per project (`HambotV2`, `BotTests`) from the restored dependency graph, covering every direct and transitive NuGet package with its exact resolved version. The `HambotV2` SBOM is the authoritative inventory of the deployed image's NuGet package set; `BotTests` SBOM findings are informational (test-only packages never reach the deployed image).
- **FR-123**: The scan shall also cover what the NuGet graph cannot see: the job builds the deployment image locally (same `HambotV2/Dockerfile` and repository-root build context) and scans it, so the report includes the ASP.NET Core runtime base image layers and the apt-installed OS packages (`postgresql-client-17`). The image is built for scanning only — never pushed to a registry, never started against production secrets.
- **FR-124**: The scan job shall scan every SBOM (and the image) for known CVEs with a non-interactive vulnerability scanner (tool choice documented in the design section) and produce one machine-readable CVE report per input. Each finding shall state the vulnerability identifier, the affected component (package or image layer) with its installed version, the fixed version where one is known, and the severity.
- **FR-125**: The scan job shall archive the SBOMs and the CVE reports per build in Jenkins with a retention policy, so the build history shows when a vulnerability entered or left the dependency tree. The build output shall include a human-readable summary of the high and critical findings (count and the findings themselves).
- **FR-126**: The scan is informational, not gating: low and medium findings never affect the build result. A high or critical finding in the deployed tree (the `HambotV2` SBOM or the image scan) shall mark the build UNSTABLE — never FAILED — and test-project (`BotTests`) findings shall not affect the build result. The operator learns about findings through the Jenkins build status and the summary output (email if the Jenkins install is configured for it); the pipeline deliberately holds no bot credentials, so there is no Discord/notification-channel route (FR-118) from the scan job.

### 2.19 Quote of the day (scheduled publication)

- **FR-127**: The bot shall support a scheduled per-guild quote publication ("quote of the day"): per-guild configuration persisted with the guild's settings (FR-24, guild-scoped like FR-26), recording the target channel, the message template (default `quote of the day: {quote}`), the publication interval (default 24 hours), the anchor time of day the schedule is aligned to (default 00:00), and the guild's time zone (an IANA time zone id, default UTC). The feature shall be active for a guild if and only if a target channel is configured — a guild without one (including after `channel clear`) gets no publications. The interval shall have a configurable minimum (`QuoteOfTheDay:MinIntervalMinutes`, default 1 minute), so cadences from quote-of-the-minute to quote-of-the-week are possible; the minimum is deployment-level configuration, not per-guild.
- **FR-128**: A `!quoteoftheday` command shall manage the configuration at runtime, with a built-in default required tier of admin (FR-33), declining in direct messages with the established "only available in servers" message (it writes guild state, FR-25/FR-50), and providing help text (FR-39, FR-40):
  - With no arguments: report the current target channel, interval, anchor time, time zone, template, and next due time — or that the feature is off (no channel configured).
  - `channel <#channel or channel id>`: set the target channel, activating the feature with the first publication at the next schedule boundary (FR-130); `channel clear` unsets it, turning the feature off.
  - `template <text...>`: set the template, which shall be non-empty, at most 500 characters, and contain the `{quote}` placeholder at least once (in-channel errors otherwise, nothing changed); the placeholder is the only one — the quote's number is part of the substituted text, like `!quote` output (FR-44).
  - `every <duration>`: set the interval, reusing the reminder duration forms (FR-62/FR-107), validated against the configurable minimum (FR-127) with an in-channel error below it.
  - `at <HH:mm>`: set the anchor time of day (24-hour clock) the schedule is aligned to, interpreted in the guild's time zone; unparseable input shall produce an in-channel error.
  - `timezone <IANA id>`: set the guild's time zone (e.g. `Europe/Berlin`); an unknown id shall produce an in-channel error.

  Interval, anchor, or time-zone changes take effect at the next boundary of the new schedule (a configuration change never triggers a mid-boundary publication); channel and template changes leave the schedule untouched. The command is subject to the standard command pipeline behavior (runtime tier adjustment FR-21, cooldown throttling NFR-12, typed argument parsing NFR-13) and, as an administrative/configuration command, is additionally exposed as a slash command when the slash surface is on (FR-110, with a typed channel option).
- **FR-129**: When due, the bot shall publish one quote into the configured channel: a random quote of that guild — the same random-fetch semantics as `!quote` (FR-44) — rendered through the configured template, each `{quote}` occurrence replaced with the number-prefixed quote text. The rendered message shall be capped at Discord's message limit, trimmed with a trailing ellipsis like the quote replies (FR-47); the stored template and quote text are never modified. A guild with no quotes at a boundary shall skip it without posting anything (logged). While maintenance mode is active (FR-98), publications shall be paused like reminder deliveries: boundaries that pass during maintenance are skipped, and the next publication happens at the next boundary after maintenance ends — no catch-up burst.
- **FR-130**: Publications shall occur on a fixed wall-clock schedule rather than drifting from the last post: the boundaries are the guild's anchor time of day plus whole multiples of the interval (FR-127), evaluated in the guild's time zone — a daily interval publishes at the same time every day (the anchor time stays put across DST shifts, e.g. 9:00 remains 9:00 after the clocks change), an hourly interval at the anchor minute of every hour, a 10-minute interval every 10 minutes from the anchor. Boundaries that passed while the bot was down or the feature was off are skipped: the next publication is at the next boundary, at most one publication per boundary — never a catch-up burst, and never drift from a late or failed post. The next due time is derived from the configuration (the next boundary after the current time), so restarts and downtime need no persisted due time.
- **FR-131**: A failed post (deleted or unavailable channel, missing Send Messages permission, a Discord error) shall be logged, skip the boundary, and leave the schedule unchanged — the next publication is attempted at the next boundary, and a late or failed post never shifts the schedule (FR-130) — and shall never crash the publication loop or the bot. A failing channel shall not disable the feature: an admin re-points or clears it via `!quoteoftheday` (FR-128). There is no upfront channel-permission validation at configuration time (the bot posts by channel id when due, and failure is handled per this requirement), and no new gateway intents are required (publication reads no channel messages).

## 3. Non-Functional Requirements

- **NFR-1 Platform**: The bot targets .NET 10 (`net10.0`) and runs as a long-lived worker service (generic host).
- **NFR-2 Configurability**: The bot name, log format, and command identifier are configurable via `appsettings.json` without code changes.
- **NFR-3 Secret handling**: The Discord token and database connection string must never be committed to the repository (`appsecrets.json` is gitignored and loaded at startup for local/source runs).
- **NFR-4 Secret-free images**: Built Docker images shall contain no secrets: containerized deployments shall receive secrets via environment variables (`Secrets__BotToken`, `ConnectionStrings__DefaultConnection`), and `appsecrets.json` shall be excluded from the publish output.
- **NFR-5 Testability**: Core command infrastructure, command naming, and permission logic shall be covered by unit tests that run without a live database or Discord connection (MSTest + Moq, in-memory configuration). The error-handling failure path and startup validation logic shall also be unit-tested.
- **NFR-6 Build & CI**: The solution shall build with `dotnet build HambotV2.sln` and tests shall run with `dotnet test HambotV2.sln` on the .NET 10 SDK. Continuous integration is provided by an existing **Jenkins server**; the Jenkins pipeline shall build and test the solution on push and must be kept up to date when the build/test setup changes. A build of a version tag (`v<major.minor.patch>`, C-5) that succeeds is auto-deployed to the server by the pipeline (verified against the known startup lines, rolling back on failure); failed builds/tests, ordinary branch pushes (including `master`), and non-version tags never deploy.
- **NFR-7 Warning-free build**: The build shall complete without nullable warnings (CS8625, CS8604, CS8620, CS0162), enabling CI to enforce warnings-as-errors.
- **NFR-8 Deployability**: The bot shall be deployable as a Docker container built from `HambotV2/Dockerfile` (repository-root build context). Given valid secrets, the container shall reach "Gateway: Ready".
- **NFR-9 Extensibility**: New commands shall be addable by implementing `ICommand` and registering it in the appropriate `Register*Commands` class, without modifying the command pipeline.
- **NFR-10 Resource isolation**: Command handling shall use per-message, transient services (handler, permission service, database context), disposed after each message.
- **NFR-11 Audit logging**: Command executions (user, command, outcome) shall be traceable from logs without debugging.
- **NFR-12 Rate limiting**: Command spam shall be throttled per user/command with a user-friendly response. The cooldown window shall be configurable per permission tier, with global per-tier defaults in `appsettings.json` and per-guild overrides adjustable at runtime via a chat command (design in [`software-design.md`](software-design.md) §3.2).
- **NFR-13 Argument parsing**: Commands shall receive typed, validated arguments through a shared parsing mechanism instead of hand-rolled `Split`/`TryParse` code.
- **NFR-14 Quotes testability**: The quotes feature shall be covered by unit tests that run without a live database or Discord connection (MSTest + Moq, EF InMemory), including: add/get/remove lifecycle with sequential numbering (including number reuse when the highest-numbered quote is removed), per-guild isolation, random fetch on a populated guild and the empty-guild message, fetch-by-number, add-by-text (including a numeric-looking argument that is out of range), text validation at the 2000-character boundary and the reply trimming of over-limit fetches and search results, search behavior and its result cap, permission gating, and DM declines.
- **NFR-15 Custom-response testability**: The custom-response feature shall be covered by unit tests that run without a live database or Discord connection, including: name/content validation, built-in collision rejection, create-vs-update behavior, removal, per-guild isolation, dispatch order (built-in wins over custom, custom wins over "unavailable"), cooldown and permission gating of response dispatch, attachment rejection (FR-60), and DM behavior.
- **NFR-16 Reminders testability**: The reminders feature shall be covered by unit tests that run without a live database or Discord connection (using `FakeTimeProvider` and EF InMemory), including: duration parsing (units, long/compact/spaced forms, sums, invalid input, non-positive durations, multi-year durations), message validation, confirmation reply, per-user isolation and caps, list and cancel behavior, due-vs-not-due delivery as time advances (including re-scheduling when an earlier reminder is added), restart recovery (a persisted due reminder is delivered when the service starts), and the bounded-failure path.
- **NFR-17 Version testability**: Version reporting shall be covered by unit tests that run without a live database or Discord connection, including: version string formatting (tag + commit hash, untagged and no-git fallbacks — pure string logic), `!version` command registration (lowercase name, help text, default tier 0), and the command's reply.
- **NFR-18 Presence testability**: The presence feature shall be covered by unit tests that run without a live Discord connection (mocked gateway client), including: startup configuration parsing and validation (invalid type, over-limit text), the `!presence` command's show/set/clear behavior with in-channel validation errors, its tier-4 gate and DM availability, update serialization, and the apply-failure path. Bio coverage (FR-113) mirrors it: `BotConfiguration:Bio` validation (including the 190-character boundary), `!bio` show/set/clear behavior, the per-guild apply against a mocked client, and the not-persisted-across-restarts semantics. Avatar and banner coverage (FR-115/FR-116) uses a fake image downloader: the attachment path and the URL path, non-image and oversized rejection, `reset`/`clear`, the per-guild apply, and failure replies.
- **NFR-19 Backup drill**: The restore procedure (FR-83) shall be scripted, documented, and proven once against a scratch database; the dump validation (FR-100) and the automated restore test (FR-101) shall be observable from service logs, and their outcomes consumable by `!health` (FR-105) and the watchdog (FR-106).
- **NFR-20 MCP testability**: The MCP feature shall be covered by unit tests that run without a live transport, database, or Discord connection, including: bearer-key rejection, each tool's behavior over fakes (EF InMemory through `IDatabaseContext`, fake Discord REST/senders), and `run_command`'s reply capture, tier-4 authority, cooldown throttling, and audit semantics.
- **NFR-21 LLM testability**: The LLM presence feature shall be covered by unit tests that run without network access (a fake LLM client), including: prompt construction, output validation at the 128-character boundary (empty, multi-line, over-limit output), interval scheduling via a fake time provider, the failure path (error → presence unchanged, next tick retries), and the feature being inactive without a configured key. Bio-update coverage (FR-114) adds: bio prompt construction, validation at the 190-character boundary (multi-line allowed), the bio failure path, and both features sharing one budget/accounting.
- **NFR-22 Backup command testability**: The backup-management commands (FR-96–FR-98) shall be covered by unit tests that run without a live database, Discord connection, or pg binaries (a fake backup manager behind the process boundary), including: on-demand backup trigger and reply, list behavior (populated, empty, the 10-entry cap), the restore two-step confirmation, maintenance-mode gating of other commands and deferred reminder deliveries, the tier-4 gate and DM availability, and failure replies.
- **NFR-23 Watchdog testability**: The watchdog, health, and notification features shall be covered by unit tests that run without a live Discord connection or database (fakes and a fake time provider), including: threshold detection for each degradation condition (gateway down, backup validation failure/overdue, restore-test failure, budget exhaustion, consecutive LLM failures, maintenance mode, notification channel unreachable), the alert-once/hourly-re-alert/recovery cadence, alert delivery to the owner DM and the notification channel via a mocked sender, the no-configured-owner log fallback, the `!health` report's fields and tier gate, notification posting per event type with the rate limit and identical-message collapse, and `!notifychannel`'s show/set/clear behavior with persistence.
- **NFR-24 Recurring-reminder testability**: Recurring reminders shall be covered by unit tests in the spirit of NFR-16 (EF InMemory, `FakeTimeProvider`), including: `every` parsing across the duration forms, the minimum-interval floor, invalid input, the creation reply, multi-cycle redelivery (delivered → re-scheduled from the delivery time, no burst after simulated downtime), numbering stability across deliveries, list marking, cancellation, the separate per-user cap, and independence from the one-shot cap.
- **NFR-25 LLM guardrail testability**: The cost and usage guardrails shall be covered by unit tests with a fake LLM client, including: per-feature/per-day accounting, budget suspension (calls stop, presence unchanged, logged) and UTC-rollover resumption, budget `0` disabling the feature set, the kill switch's `status`/`off`/`on` states with the restart-restores-config behavior, and the `!llm` replies and tier gate.
- **NFR-26 Application-command testability**: The application-command surface shall be covered by unit tests without a live Discord connection, including: the interaction→command-line mapping from option definitions (and the `arguments` fallback), execution through the pipeline with shared tier/cooldown/audit semantics (slash and text invocations of one command share a throttle key), denial ephemerality and public output, DM-scope invocations, and the registration contract (every slash-eligible command yields a valid application-command definition; ineligible commands yield none).
- **NFR-27 Scan automation**: The dependency security scan shall be defined as code in the repository (the pipeline definition, not an ad-hoc Jenkins-UI script) and shall run end-to-end non-interactively — no interactive tool prompts, no manual steps — on a weekly schedule without operator action. The required agent tooling (.NET 10 SDK, Docker, the SBOM generator, the scanner) shall be installable non-interactively and its setup documented.
- **NFR-28 Scan verification**: The scan is a pipeline-only feature and carries no `BotTests` unit tests; it is verified by a live run of the scheduled job against the repository — the acceptance run must produce the SBOMs and CVE reports, archive them with the build, and reach the build result the result policy dictates (FR-121–FR-126), without deploying or touching the running stack.
- **NFR-29 Quote-of-the-day testability**: The quote-of-the-day feature shall be covered by unit tests that run without a live database or Discord connection (EF InMemory, a fake channel sender, a fake time provider), including: template validation (empty, over 500 characters, missing `{quote}`) and rendering (number-prefixed quote text, repeated placeholders, the 2000-character trim), interval parsing across the reminder duration forms with the minimum-interval floor, scheduling (first publication at the next boundary on activation, fixed wall-clock boundaries — the same time each day across a simulated DST shift, sub-daily intervals aligned to the anchor minute, configuration changes taking effect at the next boundary, boundaries missed during downtime or maintenance skipped — one publication at the next boundary, never a burst and never drift from a late or failed post), the empty-guild skip, the failed-post path (logged, schedule unchanged, feature stays on), maintenance-mode pausing, per-guild isolation, and the command's show/set/clear behavior per subcommand (including `at` and `timezone` validation), tier gate, and DM decline.

## 4. Constraints

- **C-1**: A valid Discord bot token is required to run the bot (login occurs at startup).
- **C-2**: A reachable PostgreSQL instance is required for startup (migrations, per FR-27/FR-28) and for any command that touches persistence (including permission checks and the permission-management commands); connection defaults assume `host.docker.internal:5432` when containerized.
- **C-3**: The Message Content intent must be enabled for the bot application in the Discord developer portal for command parsing to work.
- **C-4**: Command names must be lowercase; lookups lowercase the input token.
- **C-5**: Releases are identified by git tags of the form `v<major.minor.patch>` (semver). A build's version is derived from the most recent such tag reachable from the built commit plus that commit's abbreviated hash (FR-76).

Argument errors (unparseable tier, unparseable user/ID, too few arguments) produce an in-channel error message. The quote and response-management commands manage per-guild state and decline in direct messages with the "only available in servers" message (FR-50, FR-59). An unknown command token is checked against the invoking guild's custom responses — subject to the same cooldown and permission checks — before the "unavailable" reply (FR-10, FR-54); custom responses do not apply in direct messages. The reminder commands are user-scoped and remain fully usable in direct messages (FR-71). *(Planned)* The administrative/configuration commands, the user-scoped reminder commands, and `!help` will additionally be exposed as Discord application commands (FR-110–FR-112, FR-119): the same registry, permission tiers, and cooldowns, with all replies shown ephemerally — visible only to the invoker — and a multi-page help list carrying interactive previous/next buttons. The other community-facing commands (the quote and custom-response commands, `!version`) stay text-only.

## 6. Out of Scope

The following are explicitly not provided:

- Per-channel configuration (per-guild configuration is in scope, see FR-24 to FR-26).
- Usage analytics.
- Uploaded file or image attachments in custom responses (content is text only — links, which Discord may render as embeds, are fine; FR-60).
- Any slash surface for the remaining community-facing chat commands — the quote and custom-response commands, `!version` — and custom responses as Discord application commands (the slash surface covers only administrative/configuration, user-scoped, and help commands, FR-110/FR-119).
- A human-facing web interface or admin panel (permissions are managed via chat commands only; the MCP endpoint, FR-86, is an agent-facing API for the operator's tooling, not an admin UI).
- Streaming-type presence activities (they require a stream URL; only `playing`, `watching`, `listening`, and `competing` are supported, FR-78).
- LLM conversation participation, memories, and personality beyond the `Llm:Persona` seed (FR-95) — planned future roadmap phases, intentionally outside the phase-1 LLM scope (FR-92–FR-95; see [`roadmap.md`](roadmap.md)).
- LLM-generated avatars or banners (image generation; the LLM features are text-only — images are set manually via `!avatar`/`!banner`, FR-115/FR-116).
- Automatic dependency remediation — the weekly scan reports findings (FR-121–FR-126); updating or pinning a package remains a manual operator decision, so the scan never opens a PR or edits the dependency tree.
- Bot-side (Discord) notifications from the scan pipeline — the scan job deliberately holds no bot credentials, so findings surface through the Jenkins build status and summary output only (FR-126).

Slash commands were previously listed here as out of scope; they are now an implemented feature, opt-in via `SlashCommands:Enabled` (FR-110–FR-112, §2.17).
